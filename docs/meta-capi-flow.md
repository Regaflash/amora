# Meta Conversions API — החזרת סטטוס לידים ל-Meta

מערך הנתונים של הסטודיו קיים, ואפשר לפרסם אליו אירועי סטטוס. המטרה: לומר
ל-Meta אילו לידים באמת נסגרו, כדי שהאלגוריתם יפסיק לאופטם למילויי טופס ויתחיל
לאופטם ל**זוגות שחותמים**.

זה השדרוג היחיד ברשימה שמשפר ישירות את תשואת תקציב המדיה.

## ⚠ אבטחה — לפני הכול

- **האסימון שהודבק בצ'אט ב-5.8.2026 נחשף וחייב החלפה.** אסימון CAPI מאפשר
  להזריק אירועי המרה מזויפים — כלומר להרעיל את האופטימיזציה, לא רק לקרוא נתונים.
- האסימון החדש נכנס ל-**Supabase → Edge Functions → Secrets** בשם
  `META_CAPI_TOKEN`, לצד `RESEND_API_KEY`. אם השליחה תתבצע מ-Make — בחיבור
  המאובטח של Make, לא כטקסט בתוך מודול.
- **לעולם לא בריפו, לא בקוד צד-לקוח, לא בהודעת צ'אט.** `tools/check.sh` כבר
  אוכף "אין סודות בקוד צד-לקוח" — הבדיקה הזו חייבת להישאר ירוקה.
- מזהה מערך הנתונים אינו סוד, אבל גם הוא נשאר בסביבה ולא בקבצים.

תרחיש Make `6821619` ("אמורה — טפסי לידים פייסבוק ← אוריגמי") מקבל אותו כ-

## ה-FLOW

```
טופס לידים ב-Meta
      │  (webhook, מיידי)
      ▼
Make 6821619 ──► אוריגמי   [+ meta_lead_id  ← התיקון]
      │
      │  הזוג מתקדם בצינור המכירה
      ▼
שינוי סטטוס באוריגמי
      │  (תרחישי Make שכבר קיימים ופעילים)
      ├─ 3838465  אין מענה
      ├─ 3742373  לא רלוונטי
      ├─ 3780276  פולואפ
      ├─ 3742386  שולם
      └─ 3620316  נחתם ושולם → אירוע פעיל
      │
      ▼
מודול HTTP → graph.facebook.com/<ver>/<dataset>/events
      │        Authorization: אסימון מהחיבור המאובטח
```

**נקודה מרכזית:** התרחישים בשלב הזה **כבר קיימים ופעילים**. לא בונים צינור
חדש — מוסיפים מודול HTTP אחד לכל אחד מהם.

### הכפילות שתעוות את המדידה אם לא נזהרים

ליד שנסגר עובר **שולמה מקדמה → נחתם → שולם**. שליחת אירוע המרה בכל אחד מהם
נותנת ל-Meta **שלוש המרות על זוג אחד** — והאלגוריתם יחשוב שהקמפיין מכפיל את
עצמו פי שלושה.

לכן ההמרה נשלחת **פעם אחת בלבד**, ב-"שולמה מקדמה": זו הנקודה הראשונה שבה כסף
אמיתי זז, והיא קורית בכל הזמנה אמיתית.

**הגנה שנייה, בקוד:** לכל אירוע יש `event_id` בפורמט
`<lead_id>:<שלב>` — למשל `1500308231886673:converted`. Meta מבצעת דה-דופליקציה
לפי `event_id`, כך שגם אם תרחיש ירוץ פעמיים או ייפול ויחזור, האירוע נספר פעם
אחת. חגורה ושלייקס, כי טעות כאן יקרה ואי אפשר לבטל אותה בדיעבד.

### ה-payload — אומת מול ה-API עצמו, 5.8.2026

לא נלקח מהזיכרון ולא מהתיעוד (שחסום מסביבת Claude). נשלחה בקשה אמיתית עם
האסימון של הפרויקט, ו-Meta אישרה את המבנה:

```jsonc
POST https://graph.facebook.com/v21.0/2851332215058775/events?access_token=…
{
  "data": [{
    "event_name":    "Lead",
    "event_time":    1785930150,          // unix seconds
    "action_source": "system_generated",  // המרה שקרתה אוטומטית
    "user_data":     { "lead_id": 1500308231886673 },
    "custom_data":   { "lead_event_source": "Origami", "event_source": "crm" }
  }]
}
```

**איך אנחנו יודעים שזה נכון:** עם `lead_id` מזויף (`1`) Meta החזירה
`code 100, subcode 2804036 — מזהה ליד לא תקין`. כלומר היא פירסה את הבקשה,
זיהתה אותה כאירוע ליד מ-CRM, והגיעה עד לוולידציה של המזהה. אילו המבנה היה
שגוי, השגיאה הייתה נעצרת מוקדם יותר. (הבקשה שלפניה, עם האסימון הישן, נעצרה
ב-`code 190 Bad signature` ולא הגיעה לגוף בכלל.)

**שני כללים שנלמדו מהשגיאה עצמה:**

1. `lead_id` הוא מספר שמונפק על ידי Meta. הודעת השגיאה אומרת "15 או 17 ספרות",
   אבל מזהים אמיתיים בחשבון הזה הם בני 16 ו-17 ספרות. לכן **לא** לקודד את
   הכלל "15 או 17" — לוודא רק שזו מחרוזת ספרות באורך 15–18.
2. **מזהה פגום אחד עלול להפיל את כל האצווה.** לכן: לוודא לפני שליחה, ולשלוח
   אירוע אחד בכל בקשה במקום אצוות.

### מה במכוון לא נשלח

כלי ה-Payload Helper של Meta מציע דוגמה שכוללת `em` ו-`ph` — האימייל והטלפון
של הלקוח, מוצפנים ב-SHA-256. **אנחנו לא שולחים אותם.**

`lead_id` הוא מפתח התאמה מדויק; הוספת פרטים אישיים לא מוסיפה דיוק, רק מעבירה
מידע. סעיף הפרטיות שנכתב לעמוד אומר במפורש "איננו שולחים אליה בדרך זו את שמכם,
את מספר הטלפון שלכם או את תוכן ההודעה" — והקוד חייב להתאים להבטחה, לא להפך.

לשם הבהירות, ההצפנה נדרשת עבור `em`, `ph`, `fn`, `ln`, `db`, `ge`, `ct`, `st`,
`zp`, `country`; **אסור** להצפין את `lead_id`, `fbc`, `fbp`,
`client_ip_address`, `client_user_agent`. ערכים חוקיים ל-`action_source`:
`email`, `website`, `app`, `phone_call`, `chat`, `physical_store`,
`system_generated`, `business_messaging`, `other`.

## חובה: לעדכן את privacy.html באותו שינוי

`CLAUDE.md` קובע שהשדות שהטופס אוסף מנויים ב-`privacy.html`, ושהוספת שדה מחייבת
עריכת הרשימה **באותו שינוי**. שליחת סטטוס לידים ל-Meta היא צעד גדול יותר מהוספת
שדה: זו **זרימת מידע חדשה לצד שלישי** על אדם מזוהה.

נכון להיום `privacy.html` לא מזכיר את זה. המסמך מבטיח בדיוק מה נאסף ומה נעשה
בו — ואסור שהאתר יבטיח דבר אחד בזמן שהמערכת עושה אחר. זה בדיוק הכשל שכבר תועד
כאן פעמיים (התראות הלידים, robots.txt מול terms).

**לכן:** סעיף ב-`privacy.html` שאומר שסטטוס הפנייה מוחזר ל-Meta לצורך מדידת
פרסום, בעברית פשוטה, נכתב **לפני** שהאירוע הראשון נשלח. זה גם סעיף שעו"ד צריך
לראות יחד עם שאר הטיוטות.

## שלב 3 · ~~סוכן השליחה~~ — נקודת הקצה נבנתה ונבדקה, 5.8.2026 ✓

**התוכנית המקורית כאן הייתה שגויה ותוקנה.** היא אמרה "מודול HTTP בחמשת תרחישי
הסטטוס" — כלומר **חמישה עותקים של אסימון ה-CAPI בתוך בלוprints של Make**,
מסמכים שנמשכים, נערכים ונכתבים בחזרה בשלמותם על ידי כלי שכבר מחק מודול בחשבון
הזה פעם אחת. האסימון נשאר ב-Supabase Secrets, ולכן הקריאה עברה לשם:

```
Make  ──POST {lead_id, status}──►  supabase/functions/meta-capi  ──►  Graph API
        + x-amora-capi-secret        (אסימון, ולידציה, מיפוי)
```

Make לא יודע את האסימון, לא יודע את טבלת המיפוי, ולא יכול לשלוח אירוע שגוי —
הוא שולח סטטוס גולמי ומקבל תשובה.

**התוכנית גם סתרה את עצמה:** היא אמרה להתחיל מ"שולם", בזמן שטבלת המיפוי מסמנת
את "שולם" כ-✗ (לא נשלח, בגלל הכפילות). ההתחלה היא **"שולמה מקדמה"**.

### שני סודות, שני בתים

| סוד | איפה | למה |
| --- | --- | --- |
| `META_CAPI_TOKEN` | Supabase Secrets | אישור פלטפורמה של Meta עם טווח אמיתי. לא בטבלה, לא בבלוprint |
| `meta_capi_hook_secret` | `private.settings` | ערך משותף בעל הרשאה מזערית — יכול לגרום לשליחת אירוע סטטוס לדאטהסט הזה ותו לא |

הסוד השני **נוצר בתוך Postgres** (`gen_random_uuid` כפול, 64 תווים) ולא עבר
בחלון צ'אט ולא בלוח העריכה של אף אחד. הוא נקרא דרך
`public.meta_capi_hook_secret()` — `SECURITY DEFINER`, `search_path = ''`,
EXECUTE ל-`service_role` בלבד — בדיוק התבנית של
`public.google_lead_webhook_key()` שכבר קיימת כאן. `private` אינו סכימה חשופה,
ולכן זו הדרך הנתמכת פנימה. רוטציה = משפט UPDATE אחד, בלי פריסה מחדש.

### באג שנתפס בבדיקה הראשונה — ותוקן

הגרסה הראשונה איחדה "לא הצלחתי להגיע לבסיס הנתונים" ו"הסוד לא הוגדר" לאותה
תשובה. הבדיקה הראשונה תפסה את זה מיד: הבקשה שפגעה במופע קר קיבלה
`500 not configured` בזמן שהשורה קיימת ושתי בקשות אחיות קראו אותה בהצלחה.

**זו אותה תקלה שהפרויקט הזה עשה שלוש פעמים** — דבר חסר ודבר שבור לובשים את
אותה הודעת שגיאה. יש להם תיקונים הפוכים, ולכן עכשיו יש להם תשובות הפוכות:

- `absent` (PostgREST החזיר `null`) → **500**, קבוע, בעל המערכת צריך לפעול
- `unavailable` (HTTP כשל / חריגה) → **503 + Retry-After**, זמני, הקורא ינסה שוב

ה-503 אינו קוסמטי: Make סופר 500 לעבר `maxErrors` ובסוף מכבה תרחיש. תקלת רשת
של שנייה לא אמורה לכבות דיווח המרות. נוסף גם ניסיון חוזר אחד אחרי 250ms.

### חמש בדיקות, כולן מול המערכת החיה

**למה בדיקה 4 היא ההוכחה:** `2804036` היא "מזהה ליד לא תקין". כדי להגיע אליה

**מה עוד לא קרה:** אף אירוע אמיתי לא נשלח. אף תרחיש ב-Make עדיין לא קורא
לנקודת הקצה, ולכן היא אינרטית — וזו הסיבה שסעיף הפרטיות עדיין לא נוסף.
